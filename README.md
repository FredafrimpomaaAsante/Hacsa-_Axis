# HACSA@10 Smart Operations and Engagement Platform

Python **FastAPI** backend for organizers and vendors: authentication, vendor applications, booth assignments, payments, events/sessions, role-based access, administration, and reporting.

## What this service covers

Built from the *Backend Developer 2 — Organizers & Vendors* scope:

- Organizer and vendor authentication
- Vendor applications and approvals
- Booth assignments
- Payment and transaction APIs
- Event and session management
- Role-based access controls
- Administration and reporting services

Interactive API docs are generated by FastAPI at `/docs` (Swagger UI) and `/redoc`.

## Prerequisites

- Python 3.11+ (this machine can use 3.14; install uses current PyPI wheels)
- Local MySQL 8 (no Docker in this setup)
- A MySQL user and database, for example:

```sql
CREATE DATABASE hacsa_smart_ops CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'hacsa'@'localhost' IDENTIFIED BY 'hacsa';
GRANT ALL PRIVILEGES ON hacsa_smart_ops.* TO 'hacsa'@'localhost';
FLUSH PRIVILEGES;
```

## Setup

```powershell
cd $HOME\hacsa-smart-ops
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
```

Edit `.env` if your MySQL credentials differ.

On first start the app creates tables automatically (`AUTO_CREATE_TABLES=true`) and inserts a platform admin from `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`.

Optional Alembic (same schema as `create_all`):

```powershell
alembic upgrade head
```

Optional demo records (organizer + vendor + published event + booth + payment):

```powershell
python scripts\seed.py
```

## Run

```powershell
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

- Health: `GET http://127.0.0.1:8000/health`
- Swagger: `http://127.0.0.1:8000/docs`

## Typical organizer–vendor path

1. Organizer registers (`POST /api/v1/auth/register` with `role: organizer`) and logs in.
2. Organizer creates an event, sessions, and booths.
3. Organizer publishes the event (`status: published`).
4. Vendor registers, applies to the event, waits for review.
5. Organizer approves (optionally passing `booth_id` to assign immediately).
6. Vendor initiates and confirms a booth payment.
7. Organizer or admin reads occupancy, revenue, and application reports.

Send `Authorization: Bearer <access_token>` on protected routes.
